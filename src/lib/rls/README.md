# Row-Level Security (RLS) — الحالة والتطبيق الصحيح

## الحالة الحالية

| البند | الحالة |
|------|--------|
| RLS مفعّل في القاعدة | ❌ لا (0 جدول، 0 سياسة) |
| العزل الفعلي الحالي | ✅ **على مستوى التطبيق** — كل استعلام يُرشّح بـ `tenantId` |
| `SET LOCAL` في `prisma.ts` | 🗑️ أُزيل (كان لا يعمل + يضاعف رحلات القاعدة) |

> **العزل بين المستأجرين مضمون حالياً على مستوى التطبيق** (الكود يُرشّح `tenantId` صراحةً + امتداد Prisma يحقنه للنماذج الأساسية). RLS طبقة دفاع **ثانية** اختيارية.

## لماذا لم يُفعَّل RLS تلقائياً؟

تفعيل RLS بشكل فعّال على هذا النظام (Prisma + Neon) **محفوف بالمخاطر** ويتطلّب تغييرين متلازمين:

1. **ضبط `app.tenant_id` لكل استعلام داخل نفس المعاملة.** الطريقة القديمة (`SET LOCAL` كجملة منفصلة على اتصال مجمّع) **لا تعمل**. الطريقة الصحيحة: تغليف كل استعلام في معاملة:
   ```ts
   await prisma.$transaction(async (tx) => {
     await tx.$executeRaw`SELECT set_config('app.tenant_id', ${tenantId}, true)`;
     // ... كل استعلامات الطلب عبر tx
   });
   ```
   هذا يتطلّب إعادة هيكلة طبقة الوصول للبيانات (أو اتصال مخصّص لكل طلب).

2. **`FORCE ROW LEVEL SECURITY`** — لأن التطبيق يتصل كمالك الجدول (Neon الافتراضي)، والمالك **يتجاوز RLS** افتراضياً.

⚠️ **لو فُعّل `FORCE` قبل أن يعمل ضبط `app.tenant_id` → كل استعلام يُرجع 0 صفوف → يتعطّل التطبيق بالكامل.**

## خطوات التطبيق الآمن (عند الاستعداد)

1. أنشئ **قاعدة فرع (Neon branch)** للاختبار — لا تختبر على الإنتاج.
2. طبّق آلية ضبط `app.tenant_id` (المعاملة أعلاه) في الكود.
3. شغّل `setup.sql` (الخطوة 1: السياسات).
4. فعّل `FORCE` جدولاً جدولاً واختبر تسجيل الدخول + كل صفحة.
5. عند نجاح كل شيء على قاعدة الفرع → طبّق على الإنتاج.

```bash
psql "$DATABASE_URL_BRANCH" -f src/lib/rls/setup.sql
```

## ملاحظات

- العمود `"tenantId"` (camelCase، يحتاج اقتباس مزدوج). جدول الطلبات `"orders"` (lowercase).
- عمليات Super Admin / السكربتات يجب أن تتصل باتصال يتجاوز RLS.
- أعد التشغيل بعد إضافة أي جدول جديد يملك `tenantId`.
